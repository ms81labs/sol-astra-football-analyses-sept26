# Backend runtime full-sweep audit

Date: 2026-09-10
Scope: every tracked production Python file outside test directories in the requested worktree
Mode: read-only audit; no production file was changed, and this report is this audit's only output

## Executive result

The tracked runtime surface is 356 Python files and 148,864 physical lines. The dominant simplification opportunity is not in the 32-file application package but in 309 release/evaluation scripts (118,704 lines): the repository preserves a long sequence of roadmap states as executable programs. The conservative Ponytail opportunity is 65,000-95,000 removable lines, one removable direct runtime dependency (`requests`), and two more dependencies that can likely leave the base API runtime if Parquet export is made optional (`pandas`, `fastparquet`).

The most important non-Ponytail issues are separate: the full-match result protocol permits a 1 GiB worker artifact but the host rejects anything over 64 MiB and materializes several whole copies; local review servers allow unconfined file reads and unbounded request bodies; synchronous filesystem/CV/LLM work runs inside `async` FastAPI handlers; and match creation can leave an uploaded file/database records behind when a later step fails.

## Method and coverage

- Source of truth: `git ls-files '*.py'`, excluding only paths containing a `test` or `tests` directory/name. Each of the 356 files below was read by a full-file AST/compile pass and included in definition/import/call-site scans. Application, release, core runner, research add-on, and representative members of every generated-looking script family received manual control/data-flow review; every reported symbol/protocol was then traced with repository-wide callers, including tests.
- Coverage by area: `backend/app` 32 files / 18,401 lines; `backend/release` 4 / 2,176; `backend/scripts` 309 / 118,704; other backend/root runtime 5 / 9,261; `research-addon` runtime 6 / 678.
- Script-family breakdown: `run_football_external*` 97 / 35,620 lines; `run_promoted*` 37 / 17,986; `run_touchline*` 11 / 11,726; `run_v7*` 46 / 20,964; `run_video_to_analysis*` 87 / 18,603; remaining scripts 31 / 13,805.
- Excluded: tracked test files, because the requested production-runtime scope explicitly excludes tests. Tests were still searched to identify intentional public seams and protocol expectations. Ignored `__pycache__`/`.pyc` files were skipped as generated bytecode. No tracked vendored or generated Python was found; the numerous roadmap/evaluation scripts are first-party tracked source and are therefore included, not skipped.
- Confidence labels: **high** means a direct control/data-flow or definition-only trace; **medium** means the opportunity depends on product retention, compatibility, or deployment-policy decisions.

## Ponytail audit: ranked simplification findings

### P1. Convert executable roadmap history into data and archive superseded stages

**Finding:** 309 first-party scripts occupy 118,704 lines, with near one-to-one companion tests and docs. The five named campaign families account for 278 scripts and 104,899 lines; the remaining 31 scripts add 13,805 lines. `pyproject.toml` exposes no installed entry point for this surface. Current callers are predominantly tests and operational/documentation commands, rather than `backend.app`; shared production imports are limited to explicit common modules.

**Recommendation:** keep a small number of actively supported commands and represent status/decision/report stages as versioned data consumed by shared render/validation runners. Archive immutable historical programs outside the runtime/test collection after confirming evidence-retention obligations. Do not mechanically delete all 309 files: some are active release gates and several common modules are imported by later stages.

**Estimate:** 60,000-90,000 lines removable; 0 dependencies. **Confidence: medium** (strong duplication signal, retention policy unknown).

### P3. Replace copy-pasted JSON primitives with the existing common helper

**Finding:** normalized AST matching found 98 identical seven-line `_load_json`/`load_json` functions, including the existing shared implementation at `backend/scripts/football_external_real_eval_chain_common.py:49`; 97 local copies can become imports. It also found 102 identical three-line JSON writers, 61 identical seven-line safe-integer parsers, 44 identical safe-float parsers, and 108 identical two-line candidate-root wrappers. Variants with different validation or atomicity semantics must remain separate.

**Recommendation:** first centralize only byte-for-byte-equivalent JSON readers/writers in a neutral script utility module; leave tiny time/root conversion helpers local unless a caller already imports a common module.

**Estimate:** 800-1,300 lines removable (582 net from readers alone); 0 dependencies. **Confidence: high** for exact duplicate groups.

### P4. Merge the three bespoke local review HTTP servers

**Finding:** `serve_promoted_v6_manual_review_ui.py` (383 lines), `serve_v7_1_positive_diversity_review_ui.py` (405), and `serve_football_external_soccernet_detector_miss_review_ui.py` (370) duplicate the same `ThreadingHTTPServer` lifecycle, JSON body handling, static-file response, and mutable review state. The latter pair share 321 matching lines (about 83% sequence similarity). They are standalone operator tools called from their own CLIs/tests, not application imports.

**Recommendation:** one hardened handler/server utility plus small route/state adapters. This also fixes S1 below once, instead of three times.

**Estimate:** 450-650 lines removable; 0 dependencies. **Confidence: high**.

### P6. Use the already-required `httpx` client everywhere

**Finding:** `backend/app/llm.py:368-376` dynamically imports `requests` for Ollama while the same function imports and uses `httpx` at `:383-398` for cloud calls. `httpx` is already a pinned direct dependency and broadly used by operational scripts; no other production file imports `requests`.

**Recommendation:** issue the Ollama request through `httpx`, preserve timeout/error mapping, and delete `requests` from `backend/requirements-runtime.txt` and its lock/image evidence in the same controlled release update.

**Estimate:** 1 direct runtime dependency removable; negligible line change. **Confidence: high**.

### P7. Make Parquet export dependencies optional for the API runtime

**Finding:** `backend/run_guerilla.py:8` imports `pandas` eagerly, but its only use is the optional `output_parquet` branch at `:8582-8585`. Production `backend/app/video_pipeline.py` passes no Parquet output. `fastparquet` is not imported directly; it supports that optional pandas path. Both are pinned in the base runtime requirements.

**Recommendation:** lazy-import the Parquet implementation and move `pandas`/`fastparquet` to the training/CLI feature set, after checking the Daytona image and operator commands. Rewriting this branch merely to avoid dependencies is unnecessary if the ML image already needs pandas.

**Estimate:** up to 2 base runtime dependencies removable; 0-5 lines. **Confidence: medium**.

### P8. Remove only the unneeded forwarding seams

**Finding:** `backend/app/main.py:65-68` forwards to `match_bundle.build_match_bundle` and has one local caller; `backend/app/jobs.py:15-18` and `backend/app/run_benchmarks.py:64-66` each wrap a single worker call. Some tests monkeypatch these seams, while `gpu_worker.py:1122-1125` deliberately delays the heavy CV import and should remain.

**Recommendation:** directly import the lightweight implementations where tests do not require a process boundary; retain the GPU lazy loader.

**Estimate:** 8-15 lines removable; 0 dependencies. **Confidence: medium**.

### P9. Stop transferring the sealed source archive when the worker never consumes it

**Finding:** `backend/app/remote_worker.py:151-158,200-202` builds and includes `source/source.tar` for every job. Daytona verifies every receipt file in `backend/app/daytona.py:377-393`, but `backend/app/gpu_worker.py:1170-1230,1320-1365` only consumes the manifest, input video, and runtime artifacts; source is not unpacked or executed. The image supplies the worker code independently.

**Recommendation:** remove the source member only through a versioned receipt/protocol change, or replace it with a compact source identity attestation. Verification compatibility currently requires the singleton role, so this is not a local deletion.

**Estimate:** small code reduction but potentially large per-job transfer/disk savings; 0 dependencies. **Confidence: high** on non-consumption, medium on release-policy acceptability.

## Correctness, security, and performance findings

These are intentionally separate from the Ponytail ranking; they are not arguments to delete code.

### S1. High, conditional security: local review servers expose arbitrary reads and unbounded bodies

`serve_v7_1_positive_diversity_review_ui.py:287-295,319-323` and `serve_football_external_soccernet_detector_miss_review_ui.py:254-262,286-290` accept `/source-image?path=` and pass the decoded caller-controlled path directly to `Path`/file serving without an allowlisted root. All three review servers also join the URL path to `ui_root` without resolving and checking containment, so `..` traversal can escape the UI root. POST handlers read caller-declared `Content-Length` fully into memory (`v7_1:362-368`, SoccerNet `:327-333`, promoted-v6 `:329-335`). They have no authentication/CSRF layer and accept a configurable host; impact is lower only while strictly loopback-bound.

**Fix/acceptance:** confine resolved paths to explicit artifact/UI roots, cap bodies before reading, bind loopback unless an authenticated reverse proxy is explicit, and test absolute paths, encoded `..`, symlinks, negative/oversized lengths, and a non-loopback startup refusal. **Confidence: high**.

### S2. High correctness: full-match worker/host result limits contradict each other

The worker accepts and streams a processor result up to 1 GiB (`backend/app/gpu_worker.py:68,669-782`), and Daytona transfers it using the same large-artifact allowance (`backend/app/daytona.py:1040-1077`). The host then caps the same artifact at 64 MiB (`backend/app/remote_worker.py:43-44,252-340`). Existing production-shape tests establish roughly 621,000 rows for a full match (`backend/tests/test_gpu_worker.py:1970-2038,2098-2117`); the 10,000-row fixture is already about 1.14 MiB, so linear scaling crosses 64 MiB.

The host additionally grows a `bytearray`, converts it to `bytes`, then builds the decoded JSON object. `processor.py:761-788` and later normalization copy row dictionaries again. Thus transport both rejects plausible full-match output and creates multiple whole-artifact copies.

**Fix/acceptance:** introduce a backward-compatible result manifest with separately hashed JSONL/NDJSON row artifacts plus a small metadata JSON; download/verify/import incrementally into staged persistence, atomically publish only after validation, retain protocol-v1 reading during migration. Test a synthetic >64 MiB/full-row-count artifact under a measured RSS ceiling, injected mid-stream/hash/parse/persistence failures with no partial publication, v1 compatibility, and exact row/order equivalence. **Confidence: high**.

### P1-runtime. High performance: the producer still retains the entire match graph

`backend/run_guerilla.py:7968-8063,8564-8605` appends all detection rows and later constructs filtered/enriched collections before returning a list. The worker's incremental JSON encoder reduces only the encoded-output copy; it cannot bound the CV producer graph. Host persistence then performs further copies, and `Storage.save_frames` creates a full list of model dumps (`backend/app/storage.py:588-613`).

**Fix/acceptance:** make the pipeline emit validated row batches to an owned staging artifact/store, and compute aggregates online or in bounded passes. Run a full-duration synthetic/video fixture with RSS scaling by batch size rather than frame count. **Confidence: high**.

### P2-runtime. High performance: synchronous I/O and model/network work blocks FastAPI's event loop

Many `async def` handlers call synchronous storage directly (`backend/app/main.py:796-930`), including full `frames.json` reads/validation and CSV rendering. `analyze_match` also invokes synchronous local/cloud LLM clients from `backend/app/llm.py` with timeouts up to 120 seconds. FastAPI only automatically threadpools normal `def` handlers; these calls execute in the request coroutine. Upload handling correctly uses `run_in_threadpool`, showing the intended boundary.

**Fix/acceptance:** make synchronous handlers normal `def`, or threadpool the blocking segments; prefer `httpx.AsyncClient` if analysis remains async. In a concurrency test, hold a storage/LLM call and assert a health/lightweight request and websocket progress still complete promptly. **Confidence: high**.

### C1. High correctness: create-match is not transactional across file, database, and dispatch

`backend/app/main.py:760-778` publishes the upload, then creates the match row, then job row, then dispatches it. No compensation runs if any later step fails. Depending on the injected failure, this leaves an orphan upload, a match without a job, or a queued job whose dispatch was reported as failed. Call tracing reaches `Storage.save_upload_stream`, `create_match`, `create_job` (`storage.py:360-453`) and `JobRunner.start` (`jobs.py:27-47`).

**Fix/acceptance:** stage the upload under a transaction/operation id, commit match+job in one SQLite transaction, publish the upload at the transaction boundary, and record dispatch state for retry rather than assuming process launch is atomic. Inject each boundary failure and assert no invisible orphan and an idempotent retry. **Confidence: high**.

### C2. High/medium security: wildcard CORS fronts unauthenticated mutation and compute routes

`backend/app/main.py:171-187` configures `allow_origins=["*"]`; the same app exposes unauthenticated upload, annotation, issue, bundle, analysis, and websocket operations. Browser-origin protections are therefore absent. If deployment is guaranteed loopback-only, this is a documented local-tool tradeoff; if reachable on a LAN/public interface, arbitrary websites can trigger state changes and expensive work.

**Fix/acceptance:** make allowed origins explicit in settings, reject unsafe wildcard configurations outside a declared local mode, and add origin/auth tests for HTTP and websocket routes. **Confidence: high on behavior, impact conditional on binding/network**.

### C3. Medium correctness/data safety: generic atomic JSON writes report failure after publishing success

`backend/app/storage.py:649-675` replaces the final JSON file and only then opens/fsyncs the parent directory. If directory open/fsync fails, the caller receives an exception but the new file remains published. Retrying non-idempotent annotation/issue/bundle creation can duplicate records. `save_upload_stream` already tracks publication and removes its unique final file on this path; `_write_json` lacks an equivalent transaction outcome.

**Fix/acceptance:** decide and document the durability contract. For unique creates, compensate a newly published path on post-replace failure; for replacements, compensation requires a backup/link or a transaction journal because the prior version is already gone. Inject directory-open and fsync failures and assert an unambiguous visible state/retry result. **Confidence: high**.

### C4. Medium correctness: terminal possession gaps are not scored

`backend/app/trust_crops.py:94-108` emits a gap only when a later controlled assignment closes it. A match ending in an uncontrolled run never finalizes that run, biasing gap counts/durations downward. `compute_trust_crops` is called from the application trust-crop route.

**Fix/acceptance:** finalize an open run after the loop using the last frame/time boundary; test all-uncontrolled input and a controlled prefix followed by a terminal gap. **Confidence: high**.

### C5. Medium correctness/availability: GPU progress is published only after processing completes

`backend/app/gpu_worker.py:1254-1293` collects progress in memory; `run_worker:1345-1385` calls the entire video processor before writing the progress artifact. `backend/app/remote_worker.py:444-480` blocks on Daytona execution and exposes only coarse host-side values before/after it. Polling/websocket clients therefore cannot observe the worker's stage callbacks during the long GPU operation.

**Fix/acceptance:** publish an append-only, bounded progress stream or poll a worker-side progress member while execution runs; validate monotonic sequence and redact credentials per event. Block the processor between two stages and assert the intermediate stage reaches the host before completion. **Confidence: high**.

### C6. Medium correctness: review bundles hide corruption and lose concurrent updates

`backend/app/storage.py:688-708` catches every exception while listing bundles and silently omits malformed/schema-invalid files. `update_review_bundle:735-750` is an unlocked read-modify-write, so concurrent updates through one instance can overwrite one another; deletion is not durable/atomic. Callers are the bundle CRUD and semantic-search routes.

**Fix/acceptance:** surface corruption distinctly, apply the existing per-instance locking pattern (with the documented multi-process ceiling), and give updates an expected-version/updatedAt precondition if multiple writers matter. Test malformed-file visibility and concurrent non-conflicting update behavior. **Confidence: high**.

### C7. Medium security/correctness: research add-on path policy is bypassable and checkout-specific

`research-addon/research_addon/path_guards.py:14-47` hardcodes one checkout and treats all `/tmp/` as allowed despite its narrower error text. More importantly, `research-addon/research_addon/judge.py:192-219` passes CLI `--storage-root` directly to `run_judge`, bypassing `resolve_run_root`; direct callers do the same. A delegated proof can therefore write wherever that process has permission.

**Fix/acceptance:** derive allowed roots from the actual repository/add-on root, use `Path.relative_to` after `resolve`, remove general `/tmp`, and enforce resolution inside `run_judge` rather than only in one CLI layer. Test alternate checkouts, sibling-prefix tricks, symlink escapes, and direct `run_judge` calls. **Confidence: high**.

### C8. Medium operational correctness: deploy evidence expires on every job without an in-app renewal path

`backend/app/remote_worker.py:125-144` runs deploy preflight for every job. `backend/release/preflight.py:1224-1300` validates freshness, and `backend/release/evidence.py:409-445` rejects evidence or gate timestamps older than the configured maximum (default 24 hours). An unchanged, otherwise valid release therefore stops accepting jobs after its evidence ages out. This may be deliberate compliance policy, but no request path renews evidence.

**Fix/acceptance:** either refresh evidence operationally before expiry and monitor it, or separate immutable release attestation from short-lived deployment authorization. Test the intended before/after-expiry operator workflow. **Confidence: high**.

### C9. Medium correctness/portability: import-time GUI probing in the core CV module

`backend/run_guerilla.py:21-33` calls `cv2.imshow` and creates an image during module import to infer headless mode. This means merely importing `video_pipeline` can touch a display backend, add latency, emit native warnings, or fail outside catchable Python exceptions on a broken display stack. Worker spawning already declares `QT_QPA_PLATFORM=offscreen`.

**Fix/acceptance:** use explicit configuration/environment and perform any capability check only at the CLI boundary when preview is requested. Test that importing the module never calls GUI APIs. **Confidence: high**.

### P3-runtime. Medium performance/resource safety: ZIP extraction reads full members into memory

`backend/scripts/run_football_external_soccernet_video_member_extract.py:227-263` reads an archive video member into a single `bytes` value before writing it. The label extractor uses the same whole-member pattern. These standalone acquisition tools can therefore spike memory on large or maliciously declared members; their on-demand environment/bootstrap also complicates deterministic operations.

**Fix/acceptance:** stream from `zf.open()` through `shutil.copyfileobj` with a declared/output byte limit and retain the current digest checks; test a large sparse fixture and oversized/short reads under an RSS ceiling. **Confidence: high**.

### P4-runtime. Low/medium performance: semantic search reparses every completed analytics artifact

`backend/app/main.py:1219-1269` calls `Storage.list_matches_with_analytics`; `backend/app/storage.py:840-876` loads and validates the full analytics document for every ready/completed match before searching summaries. Cost grows with all historical matches even though only the summary is needed and the result limit is 50.

**Fix/acceptance:** persist/index a compact summary at analytics-write time or select it from SQLite; benchmark query latency and bytes read across thousands of matches. **Confidence: high**.

## Compatibility notes

- P1/P2 require a retention decision: release evidence may rely on source availability even when runtime callers do not.
- P9 and S2 change sealed worker/host contracts. Add a protocol version/capability and keep v1 readers until all deployed images are upgraded; do not silently reinterpret the current `processorResultPath` or required receipt roles.
- Dependency changes alter the pinned runtime/image evidence and must go through the repository's release verification flow.
- C1 and C3 need explicit transaction semantics before implementation; deleting a just-published replacement cannot restore the overwritten prior JSON.
