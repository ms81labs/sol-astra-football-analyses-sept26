# Football analysis readiness — 13 September 2026

**Assessment: a substantial, locally verified research application, ready for controlled evaluation; general-purpose, coach-trustworthy video analysis is not yet demonstrated.**

The software foundation is considerably stronger after the September fixes. The major remaining uncertainty is whether the complete pipeline produces accurate positions, identities, ball trajectories and football events on unseen video. Existing “ready”, “closed”, “full analysis” and “passed” artifacts often establish narrower things: data access, metadata adaptation, crop localization, JSON assembly or report routing. They cannot be added together into a production accuracy claim.

This report began from source `72f554507487652521af7002c8eb4be98a5c78bf`; its executed readiness baseline now binds the source identified in [the v7.3 manifest](../../backend/release/v7.3.json), current local artifacts, and official dataset information checked on 13 September 2026. The execution added a bounded ground-truth adapter, fetched the official SoccerTrack panoramas for match `117092`, and ran a calibration-rejected first-half diagnostic. On 14 September it also acquired two additional CC BY 4.0 panoramic matches, two CC0 broadcasts and one CC0 legacy club-domain recording for the pilot inventory without running inference on held-out sources or inspecting their labels for evaluation. Subsequent frame comparison proved that the existing local clips are derivatives of `117093`, so only `118575` remains an untouched panoramic test. G-PRODUCT then completed on the declared one-minute clip through the sealed Daytona worker, including live progress, validated import, all declared API reads, and confirmed sandbox cleanup. Both intact `117092` halves subsequently completed through the same production command inside the sealed 9,000-second execution and 180-minute sandbox limits. These runs establish representative whole-match capacity across the two natural halves; they do not establish football accuracy. No run trained or promoted a model. Historical results are identified as historical. Missing evidence means **unproven**, rather than proof that a capability can never work.

## The most consequential evidence gaps

**1. “Full SoccerNet analysis” is a full video signal scan, not full football reconstruction.**

The historical execution processes 146,893 frames from a 398×224, 25 fps video—about 97.93 minutes. That is meaningful decoding and source-handling work. The actual [execution code](../../backend/scripts/run_football_external_soccernet_full_analysis_execution.py) computes brightness, green-dominant pixel ratios and frame-difference motion statistics. It does not establish detected players, tracked identities, calibrated coordinates or predicted events against labels. A full-duration scan must not be reported as full-match CV acceptance.

**2. SoccerTrack coordinates reach a reference-only bundle and a bounded runtime comparison, but the calibration check fails.**

The retained GSR files use SoccerTrack v2's shipped SoccerNet-COCO structure, not the older cached flat-record description: prefixed string `image_id` values identify one-indexed frames, identity fields live under `attributes`, and metric positions use `bbox_pitch.x_bottom_middle` / `y_bottom_middle`. Timing is half-relative. The [official format note](https://github.com/AtomScott/SoccerTrack-v2/blob/main/docs/format-gsr.md) explicitly warns that the shipped files differ from the earlier description.

The [adapter](../../backend/scripts/run_football_external_soccertrack_adapter_smoke_test.py) now streams bounded annotation windows without loading either 2.7 GB file wholesale. A retained-data run read 20 frames from each half, preserved 858 usable player/referee positions, and recorded 22 annotations whose metric position was absent. The [bundle bridge](../../backend/scripts/run_football_external_soccertrack_match_bundle_bridge_smoke.py) exported those 40 frames and 3,142 BAS events with unique cross-half frame IDs. Every GSR frame is marked `referenceOnly`; provenance states `referenceLabelsUsedForInference=false`. Inspection exposed a real format mismatch: this retained BAS file uses a global match clock and contains a third period, while the cached format prose describes half-local positions. The adapter now derives periods from the clock, so bare `90:01` is period 3 rather than being silently folded into period 2. Only global-time windows covered by the two retained videos are used below.

The matching first-half panorama was then fetched and a 100-frame slice was run through the existing pipeline without reference-seeded crops. The corrected [alignment scorer](../../backend/scripts/run_football_external_soccertrack_calibrated_alignment.py) undistorts raw fisheye foot points before applying the inverse supplied homography. Its 65 authoritative `117092` keypoints measure 4.68 m median, 25.45 m p95 and 31.05 m maximum error, failing the declared 5 m assignment tolerance. The downstream 1920 run matched 61 of 308 predictions to 418 references within 5 m (19.8% precision, 14.6% recall), but those values are diagnostic only because calibration failed. A second check reused that scorer with the official `117093` intrinsics, homography and 65 keypoints: 1.79 m median, 9.95 m p95 and 12.65 m maximum, also failing. The projection order matches the upstream fisheye-undistortion and pitch-to-calibrated-homography implementation; upstream's 8.64 px figure is the camera-model fit RMS, not this pitch-space round trip.

A validation-only repair probe fitted the homography directly in the scoring direction after official fisheye undistortion. Its in-sample p95 improved to 4.37 m on `117093`, but remained 8.12 m on `117092`. The reproducible [withheld-control-point diagnostic](../../backend/benchmark_suites/football_analysis_pilot_soccertrack_calibration_cv.json) then repeated the fit 65 times per source, training on 64 official keypoints and scoring only the excluded point. `117093` still passes the 5 m bar at 2.75 m median and 4.68 m p95 (5.80 m maximum); `117092` still fails at 3.71 m median and 8.33 m p95 (12.44 m maximum). Every calibration input is hash-bound, no held-out source or pipeline inference was accessed, and runtime calibration remains unchanged. This confirms inverse-fit bias as the dominant repairable issue for `117093`, while `117092` needs a better camera model. The repaired `117093` mapping is used only for the validation diagnostic below. Image-space MOT HOTA/IDF1 remain unavailable because no MOTChallenge ground-truth boxes are present. Official pitch-space GS-HOTA is also withheld because the application predictions lack its required role, team and jersey attributes; anonymous tracker IDs alone are insufficient.

A 15 September validation-only fit-selection spike rechecked every `117092`/`117093` keypoint and intrinsics SHA-256 against that frozen diagnostic, then repeated the same 65 leave-one-point-out folds for a raw-pixel homography and RANSAC after official fisheye undistortion. The plain corrected fit reproduced p95 errors of 8.328 m and 4.675 m. Skipping fisheye correction worsened them to 15.161 m and 12.285 m. RANSAC with a 12 px calibrated-image threshold gave 9.771 m and 4.651 m; tighter 3 px thresholds gave 18.368 m and 10.387 m. Both cameras' largest withheld errors include far-side pitch boundary corners. Thus an outlier switch or raw-pixel shortcut does not clear even the `117092` 5 m assignment bar, much less the frozen 3 m pilot pitch bar. This was an ad hoc candidate rejection, not a new benchmark or deployed camera model; no held-out source, runtime or prediction changed.

The same folds also rejected a direct nonlinear shortcut: quadratic least-squares mappings from standardized, fisheye-corrected image coordinates to pitch positions had p95 errors of 19.197 m (`117092`) and 14.422 m (`117093`); cubic mappings reduced median error but still had p95 8.626 m and 4.682 m. A lower in-sample or median error cannot replace the withheld tail criterion. No polynomial mapping was promoted.

A later validation-only residual probe fitted a direct homography and then a SciPy thin-plate-spline correction. Its earlier leave-one-keypoint-out result looked promising (2.92 m p95 on `117092`, 0.79 m on `117093`), but withholding entire pitch thirds produced 15.73/11.07 m x/y p95 on `117092` and 10.86/7.41 m on `117093`; its saved `117092-01` player matches still had 3.72 m p95. A fresh ad hoc smoothing sweep rechecked all official keypoint/intrinsics hashes against the frozen calibration diagnostic, fitted each homography and residual interpolator only on fold-training points, and tried smoothing 0, 0.001, 0.01, 0.1 and 1 on training-standardized image coordinates. Even the best x-third p95 remained 13.20 m on `117092` and 9.69 m on `117093`; the best y-third p95 was 32.54 m and 11.69 m respectively. The sweep specifies its scaling and third partitions, while the earlier spike was not retained as a frozen benchmark, so these figures are not a direct reproduction; both checks reject the claim that nearby-point interpolation establishes robust camera mapping. The sweep was shell-only, not a frozen benchmark or deployed change; no held-out source, prediction, runtime calibration or independent label was touched. Focus the next calibration work on region-generalizing camera geometry rather than smoothing this residual fit.

A validation-only keypoint-location check narrows that next repair. Both hash-checked cameras have 25/15/25 official points in far/middle/near pitch-width thirds, so regional failure is not simply an empty third. With all 65 points in the direct homography fit, the 21 far-boundary (`y=0`) controls on `117092` still have 5.120 m median and 10.274 m p95 pitch error, versus 1.421/5.740 m for the 21 near-boundary (`y=68`) controls; `117093` has 2.804/4.565 m far versus 1.947/4.036 m near. A finite +1-pixel shift in calibrated-image vertical position changes the fitted pitch projection by a median 2.387 m far versus 0.156 m near on `117092`, and 1.910 versus 0.154 m on `117093`. These are in-sample residual and local-sensitivity diagnostics, not withheld accuracy or proof that label noise caused the errors. They show why a small far-side image/footpoint error can dominate pitch metres: obtain independent far-side line/footpoint geometry, then score pitch error by region and camera before choosing a runtime correction. No held-out media, labels, predictions or runtime mapping were changed.

## Football-specific limitations to account for

- **Source coordinates and camera mode:** calibration needs measured pitch error, including pans, zooms, fisheye distortion and loss of useful field lines. A valid homography matrix can still be inaccurate. Panoramic and broadcast clips need separate score breakdowns.
- **Identity:** match statistics need stable player identities. Current frame IDs and track IDs do not establish continuity across occlusion, cuts, substitutions or halves. The inspected `MatchConfig` contains one attack direction, not an explicit per-period direction schedule; full-match operation must handle half changes deliberately.
- **Possession and events:** proximity/continuity heuristics propagate errors from ball detection and team assignment. Report visible-ball recall, inferred coverage and unknown time separately. Current confidence warnings in the report/UI are useful, but internal “trusted” status is not external validation.
- **Physical totals:** normalized coordinates are converted using 105×68 m. Check actual field dimensions and camera-derived speed jitter before using distance/top-speed/sprint totals for player assessment.
- **xG and coaching:** the current xG function uses fixed distance/angle/box bonuses. It has no demonstrated probability calibration against shot outcomes. Valid JSON and escaped HTML establish safe formatting; they do not establish factual coaching advice. Keep human review and trace recommendations to source observations.
- **Capacity and operations:** preserve real decoding/inference timings separately from report assembly. Measure failure recovery, long-run memory, staging space and GPU deletion with the full application path. The project explicitly remains local-only until G-NETWORK is satisfied.
